# Техническое задание: ContractScout

**Продукт:** бот и веб-сервис проверки IT-договоров на узкие места и генерации проекта договора на услуги.  
**Статус:** MVP + AI + расширенные функции, готов к демо и деплою.  
**Дисклеймер:** сервис не оказывает юридические услуги и не заменяет адвоката.

---

## Этап 1. Идея и исследование

### Проблема

Фрилансеры, ИП и небольшие IT-студии получают договор «как есть» от юридического отдела заказчика. В нём часто спрятаны рычаги: безлимитная ответственность, переход фоновых библиотек, бесконечные правки, оплата только после акта, личное поручительство, иностранный суд. Человек без юротдела либо подписывает вслепую, либо тратит 20–40 тысяч на разовую экспертизу.

### Аналоги и конкуренты

| Решение | Что даёт | Слабое место для нашей аудитории |
|---|---|---|
| Юрист / юротдел | Качество и ответственность | Дорого, медленно, не в мессенджере |
| ChatGPT «проверь договор» | Быстро | Нет каталога IT-рисков, нет цитат, галлюцинации, нет файла-черновика |
| Конструкторы договоров (Тильда-доки, FreshDoc) | Шаблон | Не разбирают чужой PDF |
| Западные AI-review (Spellbook, Harvey) | Сильный NLP | Английское право, ent-цена, не MAX |

### Уникальное ценностное предложение

**ContractScout — разведка узких мест, а не «замена юриста».**  
Гибрид: правиловой сканер типичных ловушек IT-контрактов РФ + RAG по собственному каталогу рисков + LLM, который обязан цитировать фрагмент. Второй режим — сразу выдать **защитный** проект договора оказания IT-услуг (лимит ответственности, IP split, автоприёмка, change request).

Канал, который уже знаком по учебным проектам: бот **MAX**. Для демо-доступа и сдачи — веб-интерфейс.

### Целевая аудитория и боли

- ИП/самозанятый разработчик: боится штрафа «1% в день без потолка».
- Студия 3–15 человек: отдаёт исходники до оплаты и теряет рычаг.
- Проджект без юротдела: не знает, какие 5 правок попросить у заказчика.

## Этап 2. Проектирование

### Функциональные требования

1. Загрузка PDF/DOCX/TXT договора.
2. Извлечение текста (Docling, fallback pypdf/python-docx).
3. Индексация чанков в векторное хранилище.
4. Отчёт: индекс риска 0–100, вердикт, узкие места с цитатой, пробелы, скрипт переговоров.
5. Мастер проекта договора IT-услуг + выгрузка DOCX.
6. MAX-бот с кнопками «Проверить» / «Проект».
7. Опциональное SMTP-уведомление о готовом отчёте.
8. Логи и health-check для деплоя.

Неребования (вне MVP): ЭЦП, распознавание сканов без OCR-качества, ответственность за исход спора.

### Архитектура

```
MAX long poll ──┐
Веб FastAPI  ───┼──► ContractScout.service
CLI/тесты    ───┘          │
                           ├─ ingest (Docling | fallback)
                           ├─ VectorStore (local JSON + MiniLM)
                           ├─ knowledge/risks.json → namespace knowledge
                           ├─ ReviewPipeline: rules + RAG + LLM
                           ├─ DraftPipeline: шаблон ГК-39 + LLM
                           └─ notify SMTP
```

Пользовательский договор живёт в namespace `contract:{user_id}`. Каталог рисков — в `knowledge`. Так RAG не смешивает чужие файлы с методичкой.

### Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Канал | MAX + FastAPI | Продолжение учебных ботов; веб нужен для демо-ссылки |
| Парсинг | Docling (Haystack converter) | Уже освоен в `hay_docling` / `hay_team` |
| Fallback | pypdf, python-docx | Демо и тесты без тяжёлого Docling |
| Эмбеддинги | multilingual MiniLM | Русский текст, без оплаты, как в локальном RAG MaxVkContentBot |
| LLM | DeepSeek chat (OpenAI SDK) | Тот же ключ, что в учебных проектах |
| Хранилище | JSON-векторка | VPS без Pinecone; Pinecone оставлен как опция в ТЗ |
| Документ на выход | python-docx | Привычный формат для юриста заказчика |
| Деплой | Docker Compose | Один порт 8080 |

### Схема отчёта (контракт API)

`POST /api/review` → сохранить в архив (локальный сканер, без ИИ): `{ id, text, report, ... }`.

`GET /api/projects` · `GET /api/projects/{id}` · `POST /api/projects/{id}/ai` → отчёт ИИ.

`POST /api/draft` → `{ markdown, docx_url }` (черновик тоже попадает в архив).

## Этап 3. MVP

Минимальный набор:

1. Правиловой сканер по `knowledge/risks.json` (работает даже без ключа LLM).
2. Веб: загрузка файла → карточки рисков.
3. Шаблон договора с защитными клаузулами (автоприёмка, cap ответственности, IP split).

Реализовано в `contract_scout/knowledge.py`, `review.py`, `draft.py`, `web/`.

## Этап 4. AI-интеграция

Где AI даёт прирост:

- формулирует *почему* пункт опасен языком фаундера;
- вытаскивает цитату, а не только keyword;
- пишет скрипт письма заказчику;
- наполняет черновик договора под бриф, не ломая защитные нормы.

Промпты: `REVIEW_PROMPT` и `DRAFT_PROMPT` в коде. Температура 0.2–0.3. Если JSON сломан — откат на rule-only отчёт (устойчивость).

## Этап 5. Расширенная функциональность

- MAX-бот (тот же UX, что учебные домашки).
- Выгрузка DOCX.
- SMTP-письмо с вердиктом (`NOTIFY_TO`).
- Каталог из 20 IT-специфичных рисков, не общий «проверь NDA».
- Скрипт переговоров в отчёте.
- Локальный архив проектов и загруженных договоров: сначала просмотр текста, затем опциональная проверка в ИИ (`POST /api/projects/{id}/ai`).
- Опциональный Pinecone: индекс обезличенных чанков для поиска; источник правды — `data/projects`.
- Сервер: `PUBLIC_BASE_URL`, reverse proxy, опциональная ЮKassa (`/api/billing/webhook`, кредиты на ИИ и черновик).

## Этап 6. Тестирование

Автотесты без сети:

```bash
pytest -q
```

Покрыто: срабатывание сканера на `samples/risky_it_contract.txt`, парсинг JSON из markdown-ограды, наличие cap в шаблоне, пробелы на пустом тексте.

Ручной сценарий: загрузить sample → индекс ≥ 70 → сгенерировать черновик → скачать DOCX. Собрать фидбек: «не хватает пункта про open-source лицензии» — задел в бэклог каталога.
